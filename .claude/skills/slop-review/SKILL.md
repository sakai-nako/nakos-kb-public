# Slop Review Workflow（AI Slop レビューフロー）

AI で下書きした実用文を、公開前に対話的かつ段階的に「臭み抜き」するためのワークフローです。

前提として [.claude/anti-slop/](../../anti-slop/) を SSOT として参照します（[00-core.md](../../anti-slop/00-core.md) の 5 軸、[01-phrases.md](../../anti-slop/01-phrases.md) の撲滅語彙、[02-structures.md](../../anti-slop/02-structures.md) の構造パターン、媒体別アダプタ [10-blog](../../anti-slop/10-blog.md) / [20-slides](../../anti-slop/20-slides.md)）。本スキルはそれらを置き換えず、「公開前レビュー」という作業フローを規定します。

---

## 起動条件

ユーザーが実用文の Slop 抜き作業を始める意思を示したとき:

- 「AI 臭抜きたい」「AI 臭がする」「AI っぽい」
- 「公開前にレビューして」「公開前チェック」「最終チェック」「校正して」
- 「ブログ仕上げて」「記事を磨きたい」
- 「Slop チェックして」「slop-review」
- 「もっと自分の声にしたい」「もっと人間っぽく」
- ブログ記事ファイル（`src/content/blog/`、`content-external/articles/`）を開いた状態で「だいたいできた」「一通り書けた」など完成を匂わせる発言

**対象は原則 1 ファイル**。複数を一度に対象にしたい場合はユーザーに明示的に確認する。

### 小説への誘導

ユーザーが `src/content/novels/` 配下の章を渡してきた場合、**slop-review は適用しない**で [novel-revision Skill](../novel-revision/SKILL.md) を案内する:

> 小説の文章レビューは novel-revision が担当します（小説では反復・断片化・修辞疑問などが意図的な作家性として機能するため、Slop の規範を当てると破綻します）。novel-revision を起動しますか？

理由詳細は [anti-slop/90-principles.md](../../anti-slop/90-principles.md) 原則 2。

---

## 全体方針（テンポ優先）

ユーザーはテンポを重視する。novel-revision と同じ流儀で進める。

- **論点を 2-3 個に絞って提示する** — 一度に 5 つも 6 つも出さない
- **ユーザーが選択した論点だけを修正する** — 全部直そうとしない
- **修正は最小単位** — 1 文〜数文の編集に留め、段落全体の再構成のような大きい書き換えは原則しない
- **構成（流れ・組み立て）には踏み込まない** — Slop レビューは文章レベル。構成は [story-structure Skill](../story-structure/SKILL.md) の領分
- **既存スタイル規約を尊重する** — ベタ詰め・ニッチ趣味の扱い・存命作曲者敬称は維持（[anti-slop/10-blog.md](../../anti-slop/10-blog.md) の整合節）

このリズムが崩れる動きはやらない:
- ❌ 論点を一気に 6 つ出して「どうですか」
- ❌ ユーザーが選んでない論点を「ついでに」直す
- ❌ 段落全体を書き換えた diff を提示する
- ❌ 「全部直しておきました」と事後報告する
- ❌ ベタ詰めを「読みやすさのため」に半角スペース挿入で崩す

## 5 軸スコアリングの使い方

[anti-slop/00-core.md](../../anti-slop/00-core.md) の 5 軸（立場 / リズム / 主体性 / 具体性 / 削減）は、**対話のフック**として使う。機械的にカウントしない。

- フェーズ 0 で初読時に暗黙評価（「立場 6/10、削減 4/10 という印象です」のように軽く伝える）
- フェーズ 1〜5 で各軸を直す
- フェーズ 6 で再評価して最終 diff まとめ

数字は会話の取っ掛かりにすぎないので、ユーザーが「数字いらない」と言ったら出さない。

## フェーズ

### フェーズ 0: 初期スキャン

ユーザーが対象ファイルを明示していない場合、まず確認する:

- IDE で開かれているファイル（`<ide_opened_file>` から取得可能）
- 直近で編集されたブログ／記事ファイル（`git status` / `git log`）

対象が小説の場合は novel-revision に誘導（上記参照）。

対象が決まったら:

1. ファイル本文を **Read** で読む
2. 媒体を判定（ブログ / 記事下書き / トーク原稿 / スライド本文 / SNS / abstract）
3. 該当する媒体別アダプタを頭に入れる:
   - ブログ・記事: [10-blog.md](../../anti-slop/10-blog.md)
   - 発表資料: [20-slides.md](../../anti-slop/20-slides.md)
4. 5 軸の暗黙評価を 1〜2 行で共有

```
ざっと読みました（媒体: ブログ）。

5 軸の暗黙評価:
- 立場 6/10、主体性 5/10、構造 7/10、具体性 6/10、削減 4/10

特に削減と主体性が低めです。立場と主体性から見ますか？
```

### フェーズ 1: 立場（Stance）

[anti-slop/00-core.md](../../anti-slop/00-core.md) の最上位軸。反証可能な具体的主張があるか。

論点提示の定型フォーマット:

```
### フェーズ 1（立場）で見つけた論点

**(a) リード段落の主張がぼやけている**
「私たちは AI と向き合う必要がある」 — 誰がどう反論できるか不明確。
→ 「PR レビューの 8 割を Claude に任せて 2 週間経った。失敗はこの 3 つだった」のように、固有の場面と主張に降ろす案。

**(b) 結論の「重要だ」が抽象的**
「○○は重要だ」 — 反論する人がいない。
→ 「○○をやらないと △△ が起きる」のように、不利益を具体的に書く案。

---

a は段落の書き直し、b は 1 文の差し替え。どれから手を付けますか？
```

論点ラベルは a, b, c, ... と通し番号で運用すると、ユーザーがあとで参照しやすい（フェーズをまたいでも振り直さない: a, b → c, d, e → f, g, h → ...）。

### フェーズ 2: 主体性（Agency）

誰が何をしたかが明示されているか。傍観者視点になっていないか。

チェック観点（[anti-slop/02-structures.md](../../anti-slop/02-structures.md) §6 と連動）:

- 主語が「私たち」「読者」「業界」など漠然としていないか
- 体験談で「私」が消えていないか
- 受け身・状態描写で誰がやったかをぼかしていないか
- 「○○が起きた」「○○が起こる」が連続していないか

### フェーズ 3: 構造（Structure）

[anti-slop/02-structures.md](../../anti-slop/02-structures.md) の 10 パターンから、特に頻出するものを 2-3 個ピックアップ:

- 否定的並列「X ではなく Y」の反復
- 修辞的疑問 → 自答
- 三連畳み込み
- 均一段落（全段落が同じ長さ・温度）
- 劇的断片化（1 文段落の濫用）
- フラクタル要約（節ごとに前段落を要約）
- 偽の脆弱性

`Grep` で「ではなく」「重要なのは」「結論として」などの頻度を出して論点化する。

### フェーズ 4: 語彙（Vocabulary）

[anti-slop/01-phrases.md](../../anti-slop/01-phrases.md) の撲滅リストから、出現しているものを論点化する。

`Grep` で候補語の頻度を出し、ヒット箇所を提示:

- 大げさ昇華語: 「教えてくれること」「本質」「美学」「境地」「風景」
- AI 常套副詞: 「静かに」「深く」「根本的に」「興味深いことに」
- 空虚な動詞句: 「役割を果たす」「機能する」「位置づけられる」
- メタコメント: 「ここで重要なのは」「結論から言うと」「実はここがポイント」
- 翻訳調: 「〜することができる」「〜を行う」「〜という事実」

頻度の絶対値より「**短い区間で密集しているか**」を見る。

### フェーズ 5: 記号・装飾（Symbols）

[anti-slop/20-slides.md](../../anti-slop/20-slides.md) と [anti-slop/03-tropes.md](../../anti-slop/03-tropes.md) §5 から:

- em-dash / `――` の多用（ブログで 5 個以上、スライドで 1 ページに 2 個以上）
- 全角ダッシュ `──` の連発
- 太字始まりの箇条書きが 3 リスト連続
- → の連射（1 ページに 3 個以上）

⚠️ **ベタ詰めは触らない**: 英数字前後・強調 `**...**` 前後の半角スペースは [anti-slop/10-blog.md](../../anti-slop/10-blog.md) の整合節通り維持する。Slop チェックで半角スペースを足してしまう癖が AI 側にあるので意識する。

### フェーズ 6: 通し読み + 最終差分まとめ

5 軸を一通り終えたら、頭から 1 周ナメる。5 軸スコアを再評価して終了。

```
### 最終差分まとめ

**フェーズ 1（立場）:**
- (a) リード段落を「PR レビューの 8 割を Claude に任せて…」に書き換え
- (b) 結論の「重要だ」を「○○をやらないと△△」に置換

**フェーズ 2（主体性）:**
- (c) 「私たちは○○すべき」→「自分は今週○○した」
- (d) 段落 4 の受け身を能動に

**フェーズ 3（構造）:**
- (e) 否定的並列を 3 箇所 → 1 箇所に削減
- (f) 1 文段落 4 つ → 2 つに統合

**フェーズ 4（語彙）:**
- (g) 「教えてくれること」→「やってわかったこと」
- (h) 「実は」3 箇所削除

**フェーズ 5（記号）:**
- (i) em-dash 8 個 → 2 個に削減

---

5 軸再評価: 立場 6→8、主体性 5→8、構造 7→8、具体性 6→7、削減 4→7
合計 28 → 38（書き直しライン 35 をクリア）
```

## 振る舞いのコツ

### やってはいけないこと

- **構成（流れ・組み立て）に踏み込まない** — Slop レビューは文章レベル。構成の話は [story-structure Skill](../story-structure/SKILL.md) を提案する
- **小説に Slop の規範を当てない** — novel-revision に誘導する
- **ベタ詰めを崩さない** — 英数字・強調前後の半角スペース挿入は [anti-slop/10-blog.md](../../anti-slop/10-blog.md) の規約違反
- **「弱み → 武器」型のナラティブに寄せない** — ニッチ趣味・女装の扱いで AI が好む構造。出てきたらユーザーに確認
- **論点を 5 つも 6 つも一度に出さない**
- **ユーザーが選んでない論点を勝手に直さない**

### やったほうがいいこと

- **5 軸のどれを直しているか名指しする** — 「これは主体性（フェーズ 2）の話です」
- **論点にトレードオフを 1 行添える** — 「a は段落書き直し、b は 1 文差し替え」
- **修正案は具体例つきで** — `→ 例: 〜` の形で代替案を示す
- **複数の Edit を並列実行できる時は並列で** — 互いに干渉しない位置の修正は 1 メッセージにまとめて投げる
- **Grep を使って頻度ベースで論点化する** — 主観でなく数で語る
- **既存スタイル規約に矛盾しないか毎フェーズで自問する** — 特に語彙・記号フェーズ

---

## 終了条件

以下のいずれか:

- ユーザーが「もういい」「これで OK」「これで公開する」と宣言
- 5 軸スコアが目標（合計 38 以上 / 全軸 7 以上）に到達
- ユーザーから別タスクへの移行サインが出る
