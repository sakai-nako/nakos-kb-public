# Coherence Review Workflow（接続度レビューフロー）

文章の要素間の **接続度（coherence / cohesion）** を対話的に診断・改善するワークフロー。

前提として [.claude/coherence/](../../coherence/) を SSOT として参照する（[00-core](../../coherence/00-core.md) の 5 要素、[01-connection-types](../../coherence/01-connection-types.md) の RST 接続タイプ辞書、[02-symptoms](../../coherence/02-symptoms.md) の症状パターン辞書、媒体別アダプタ [10-blog](../../coherence/10-blog.md) / [20-slides](../../coherence/20-slides.md)、原則 [90-principles](../../coherence/90-principles.md)）。本スキルは「公開前・推敲時の接続度レビュー」という作業フローを規定する。

---

## 起動条件

ユーザーが要素間の接続度に違和感を表明したとき:

- 「接続度を見て」「coherence チェック」「coherence-review」
- 「つながりが弱い箇所を探して」「論理が飛躍している気がする」
- 「先出しした情報が後で生きない」「読んでいて『なぜここで？』と詰まる」
- 「文章の流れがぎこちない」「並んでいる順序が変な気がする」
- 構成（story）は決まっていて、流れの磨きを依頼されたとき

**対象は原則 1 ファイル**。複数を一度に対象にしたい場合はユーザーに明示的に確認する。

### 他の Skill への誘導

- **構成（プロット・章立て・伏線・幹）の相談**: [story-structure Skill](../story-structure/SKILL.md) に誘導
  - 「ここに新しい章を入れるべき」「全体の流れを変えるべき」のようなマクロ修正は coherence の範囲外
- **語彙・記号・装飾の磨き**: [slop-review Skill](../slop-review/SKILL.md) に誘導
  - 「『ふと』が AI 副詞」「`──` が多い」のような語彙・記号レベルの話
- **小説の章**: [novel-revision Skill](../skills/novel-revision/SKILL.md) に誘導（理由詳細は [coherence/90-principles.md](../../coherence/90-principles.md) 原則 2）

---

## 全体方針（テンポ優先）

ユーザーはテンポを重視する。[novel-revision Skill](../novel-revision/SKILL.md) / [slop-review Skill](../slop-review/SKILL.md) と同じ流儀で進める。

- **ワースト 3 程度に絞って提示する** — 全部の接続を直そうとしない（[coherence/90-principles.md](../../coherence/90-principles.md) 原則 8）
- **修正は最小単位** — 1 文〜数文の編集に留め、段落全体の再構成のような大きい書き換えは避ける
- **トレードオフを明示** — 修正で失うものを必ず併記（原則 6）
- **構成・語彙には踏み込まない** — 接続だけに集中（原則 9）
- **既存スタイル規約を維持** — ベタ詰め・Markdown 装飾なし・所要時間なし、等（原則 1）

このリズムが崩れる動きはやらない:
- ❌ ワースト 10 個を一気に出して「どうですか」
- ❌ ユーザーが選んでない箇所を「ついでに」直す
- ❌ 段落全体を書き換えた diff を提示する
- ❌ 「全部直しておきました」と事後報告する
- ❌ 構成変更を提案する（story-structure の領分）
- ❌ ベタ詰めを「読みやすさのため」に半角スペース挿入で崩す

## フェーズ

### フェーズ 0: 初期スキャン

ユーザーが対象ファイルを明示していない場合、まず確認する:

- IDE で開かれているファイル
- 直近で編集されたファイル（`git status` / `git log`）

対象が小説の場合は novel-revision に誘導（上記参照）。

対象が決まったら:

1. ファイル本文を **Read** で読む
2. 媒体を判定（ブログ / 記事下書き / CFP abstract / スライド原稿）
3. 該当する媒体別アダプタを頭に入れる:
   - ブログ・記事・CFP abstract: [10-blog.md](../../coherence/10-blog.md)
   - スライド: [20-slides.md](../../coherence/20-slides.md)
4. 文章を粒度ごとに分解（段落・文・句）

### フェーズ 1: 接続マップ作成

段落間の接続マップを表形式で作成。各遷移に:
- **接続タイプ**（[01-connection-types.md](../../coherence/01-connection-types.md) から選ぶ、複合可）
- **接続度スコア** 0-10
- **接続を支える要素**（観察可能な要素のみ: 共有語彙・接続詞・指示語）
- **接続を弱める要素**
- **1 行コメント**

例:

```
### 段落間 接続マップ

| 遷移 | タイプ | スコア | 支える要素 | 弱める要素 | コメント |
| :--- | :--- | :---: | :--- | :--- | :--- |
| 段1→段2 | Background+Elaboration | 4 | 「気が重い」→「気重」の語彙反復 | 「本職SRE」が問い「リハ気重」と直接結びつかず文頭で浮く | Buried Setup |
| 段2→段3 | Setup-Payoff | 7 | 「気合いでやるリハ、再現性なし」が運用語彙で Toil への橋 | 段2で浮いていた SRE がここでようやく回収 | 遅れた接続 |
| ... | ... | ... | ... | ... | ... |
```

スコア 5 未満があれば、その段落の内部（文間）に降りて二段目の接続マップを作る:

```
### 段落2 内部 文間マップ（スコア5未満のみ）

| 遷移 | タイプ | スコア | 弱める要素 |
| :--- | :--- | :---: | :--- |
| 文1→文2 | Concession（形式のみ） | 3 | 「のですが」が形式的に繋ぐだけで、SRE と「アドリブに弱い」に意味的橋なし |
```

### フェーズ 2: ワースト N の特定 + 症状の診断

接続度の低い遷移を **3-5 個**（または合意した数）抽出。各ワーストについて症状を [02-symptoms.md](../../coherence/02-symptoms.md) のカタログから特定:

- 先出し未回収（Buried Setup）
- メタファー論理橋省略
- 抽象-具体順序逆転（Restatement Loop）
- 共有概念途切れ（Lexical Chain Break）
- 逆接の乱用（Faux Concession）
- 唐突な話題転換（Topic Jump）
- 後出しの過剰情報（Late Loading）
- 対称構文の擬似接続（Symmetric Stuffing）

ユーザーに「このワースト N から、どれを直しますか」と確認:

```
### 接続度ワースト 3

**W1: 段2「本職SRE → アドリブに弱い」接続度 3（症状: 逆接の乱用 + 先出し未回収）**
- 「のですが」が形式的に繋ぐだけで意味的橋なし
- SRE は段3「Toilじゃないか？」の Setup として置かれているが、配置時点で浮く

**W2: 段5「一発で回ります → Vue製のSlide-as-Code」接続度 3（症状: 唐突な話題転換）**
- 共有概念が「Slidev」一語のみ

**W3: 段5末「Component や SSOT」→ 段6「Single Source of Truth」接続度 5（症状: 抽象-具体順序逆転）**
- 同一概念が二段落連続

---

どれから手を付けますか？
```

ワーストラベルは W1, W2, W3, ... と通し番号で。

### フェーズ 3: 修正案提示

選ばれたワーストごとに、修正アクション（A 接続橋 / B 移動 / C タイプ変更 / D 削除）を 1-3 案提示。各案に:
- **修正後の具体テキスト**（「こんな感じで」ではなく完成形）
- **トレードオフ**（その修正で失うもの）
- **推奨案とその理由**

例:

```
### W1 修正案

**A 案（接続橋）**:
「本職はインフラ屋でSRE ─ 反復作業を削るのが日課です。なのに、白状すると、自分の登壇では削れません。アドリブに弱いくせに、…」
- 効果: Antithesis（運用では削るのに自分の登壇では削れない）で配置時点で意味接続成立
- トレードオフ: 字数増（+30 字）、段3「Toilじゃないか？」発見の鋭さがやや前借り
- 「Toil」用語は段3で初出に温存することで、Setup-Payoff の鋭さは維持

**B 案（移動）**: SRE を段3へ移動
- トレードオフ: 「誰が話すか」が遅れ、CFP 審査者目線では親切でなくなる

**推奨**: A 案（バランス最良）
```

ユーザーが選択 → Edit で適用。

### フェーズ 4: 改善後の検証

修正後の接続マップを再評価。スコアの推移をユーザーに共有:

```
### 修正後の接続度推移

- W1: 段2「本職SRE → アドリブ」: 3 → 8
- W2: 段5「一発で回ります → Vue製」: 3 → 8
- W3: 段5末「Component や SSOT」 → 段6: 5 → 8

新たに浮いた箇所はなし。Coherence と Cohesion の両輪が成立した状態。
```

新たに問題が出ていないか（修正の副作用）も確認。

## 振る舞いのコツ

### やってはいけないこと

- **構成や流れ（マクロ）に踏み込まない** — story-structure の領分（原則 9）
- **語彙・記号・装飾の話に流れない** — slop-review の領分
- **小説に適用しない** — 作家性として意図的な飛躍が機能する（原則 2）
- **接続マップを主観で作る** — 観察可能な要素（共有語彙・接続詞・指示語）で根拠を示す（原則 7）
- **修正案にトレードオフを書かない** — 失うものを必ず書く（原則 6）
- **ワースト全部を一度に直そうとしない** — 上位 3 つに絞る（原則 8）

### やったほうがいいこと

- **接続タイプは複合で記述** — 「Background + Elaboration」「Concession + Antithesis」のように（原則 5）
- **スコアの根拠を示す** — 「7: 接続詞と共有語彙はあるが、論理の橋が一段弱い」のように
- **症状名を明示** — [02-symptoms.md](../../coherence/02-symptoms.md) のカタログから選ぶ
- **修正後のテキストを具体的に提示** — 「こんな感じで」ではなく完成形を出す
- **修正は並列 Edit で** — 複数箇所の互いに干渉しない修正は 1 メッセージで投げる
- **「Cohesion 強・Coherence 弱」を疑う** — AI 下書きの典型パターン（原則 4）

---

## 終了条件

以下のいずれか:

- ユーザーが「これで OK」「これで公開する」と宣言
- ワースト全てが接続度 7+ に到達
- 別タスクへの移行サインが出る
