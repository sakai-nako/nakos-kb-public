# Writing Style（フィードバック由来の表記・言い回し規約）

セッション中のユーザーフィードバックから確立した文章スタイル規約の **Single Source of Truth** です。もともと Claude Code のローカルメモリ（`feedback_*` 系）に蓄積していた学びを、**モデルやツールが変わっても参照できるように** リポジトリへ移管しました（2026-07）。

- 新しいフィードバックが出たら、このファイルに **Why / How to apply / 出典** の 3 点セットで追記します。取り込み手順は [docs/learnings/README.md](../../docs/learnings/README.md) の「フィードバックの取り込み」を参照。
- 機械的に検査できる規約（§1・§2 の一部・§3）は `just check-content`（[scripts/check-content.mjs](../../scripts/check-content.mjs)）でも検査されます。§7 に対応表があります。

## 1. ベタ詰め（英数字・記号の前後スペース）

**対象**: ブログ・記事・CFP 提出本文（タイトル + トーク概要）

本文中の半角英数字（数字・アルファベット・`CfP` のような語）、強調記号 `**...**`、半角括弧 `(...)`、半角引用符 `"..."` と日本語の境界には、半角スペースを入れず **ベタ詰め** にする。

| NG | OK |
| :--- | :--- |
| `30 分` | `30分` |
| `CfP を` | `CfPを` |
| `**地続き** です` | `**地続き**です` |
| `コードの "向こう側" に` | `コードの"向こう側"に` |
| `リポジトリ (公開ミラー)` | `リポジトリ(公開ミラー)` |

**保持する（例外）:**

1. 英語フレーズ内のスペース — `SRE Kaigi`、`CloudNative Days`、`Rust + Bevy + Dioxus desktop`、`Single Source of Truth` など
2. 行頭のリスト・見出しマーカーのスペース
3. em-dash `—`・全角ダッシュ `──`・矢印 `→` 等の構造的な区切りスペース
4. 日本語と記号（`？` `！` `─` 等）の境界の意図的な区切りスペース — 例: `『これ、どこに置けばいい？ 半年後の自分は…』`

**Why**: 日本語組版でのベタ詰めを好む明確な嗜好。AI 側には「読みやすさのため」に半角スペースを挿入する癖があるので、レビュー時にスペースを**足さない**ことも含めて規約。

**適用範囲の補足**: CFP の `drafts.md`（校正過程）や作業ログセクションは作業メモなので必須適用ではない。最終提出本文（タイトル + 概要）はベタ詰め必須。

**出典**: 2026-05-24 クラウドネイティブ会議 登壇プロセス編ブログの推敲で明示指示。2026-06-27 フロントエンドカンファレンス関西 CFP ブラッシュアップで CFP abstract まで適用拡張を確認。

## 2. CFP 提出本文の表記

### 2.1 Markdown 装飾を使わない

CFP の提出本文（タイトル + トーク概要）には Markdown 装飾（強調 `**...**`、インラインコード、`###` 以下の見出し、リスト `-` `*`、引用 `>`）を使わず、**プレーンテキスト** で書く。`index.md` の構造用 `##` 見出し（「トークタイトル」「トーク概要」）だけは許可。

強調したいフレーズは装飾ではなく次の手段で立てる:

1. **引用括弧「」で囲む** — 例: 「持ち込むのはWeb。守るのはRust。」
2. **独立段落として配置** — 例: 「リハは気合いでやらない。回す。」を独立段落に
3. **文脈で立たせる** — 例: 「── 3つの守護者」のように em-dash で受ける構造で集約

**Why**: 装飾よりも内容にフォーカスしたい。CNK 2026 採択 abstract も装飾なしのプレーン本文で運用。fortee 等のプラットフォームが Markdown レンダリングに対応していても装飾依存にしない。

**適用範囲の補足**: `drafts.md`（校正過程）と `_memo.md` は装飾を使ってよい。対象はあくまで **CFP として外に出る本文**。2026-06 より前の CFP 3 本（sre-kaigi-2025 / one-stop-output / cnk-sre-observability）は提出済みの実物アーカイブなので当時のまま残す（機械チェックでも免除）。

**出典**: 2026-06 フロントエンドカンファレンス関西 CFP ブラッシュアップ。

### 2.2 所要時間を書かない

abstract / トーク概要本文に「30分で共有します」「5分で」のような **所要時間表記を書かない**。応募フォームで枠（LT / レギュラー）を選択している以上、本文で時間を書くのは情報の二重提示で冗長。「本セッションでは、◯◯を共有します。」で締める。

タイトルに「5分」を入れる演出（例: 「〜した5分」）は別物として許容（タイトルは語呂・リズムの最適化対象）。

**出典**: 2026-06 フロントエンドカンファレンス関西 CFP ブラッシュアップ。

### 2.3 3 ファイル構成

CFP のディレクトリ構成（`index.md` / `drafts.md` / `_memo.md`）の詳細は [16-content-locations.md](./16-content-locations.md) §3 と [docs/cfp/playbook.md](../../docs/cfp/playbook.md) を参照（そちらが SSOT）。

## 3. 作業日付を本文に書かない

サイトに出るコンテンツ本文に編集日時・レビュー実施日などの **作業日付を載せない**。SSOT は [16-content-locations.md](./16-content-locations.md) §4。要点だけ再掲:

- `### Round 1 改善ログ (2026-06-27)` → NG。`### Round 1 改善ログ（型適合）` のように観点でラベリング
- コンテンツとしての日付（開催日・公開日・応募日）と frontmatter のメタ日付は OK
- 「特定時点のスナップショット」性が内容と一体のドキュメント（self-portrait 等）のセッション日付は事実日付として OK

## 4. 小説: 実在楽曲は物語に従属させない（cadenza-engineering）

各話が実在のクラシック / 吹奏楽曲をモチーフにする連作では、**曲=主体、物語=受け取る側** の向きを一貫させる。「この物語に差し出された楽曲」のような、曲を物語のために用意された道具・従属物にする言い回しを避ける（採用例: 「この物語が受け取った楽曲」）。

動詞は各話で違ってよい（作中で曲が物語を導く描写に沿うなら「この物語を導いた楽曲」も OK）。要は曲を従属させないこと。

**Why**: 曲は実在し独立して先に在るもので、物語はそれに着想を得て受け取った側。

**出典**: cadenza-engineering の楽曲ラベル推敲でユーザーが「差し出された」を却下し「受け取った」に修正。

## 5. 人物・題材の扱い

### 5.1 女装・ニッチ趣味は堂々の個性として扱う

女装やニッチ趣味（と技術の接続）は、隠したい弱みではなく **何度も登壇で見せている堂々とした個性・武器**。「弱みだと思っていたものが武器だった」「隠していたものを見せる」という告白・弱みの開示の枠で書くと違和感を与える。AI が好みがちな「弱み → 武器」型ナラティブが出てきたら要注意。

**出典**: 2026-05 社内発表スライド作成時の指摘（「女装して登壇するのは結構やっていて、弱みでも隠したいことでもない」）。

### 5.2 存命作曲者には敬称を付ける

自分の地の文（SNS 告知・ブログ本文）で実在の作曲者に言及するとき、**存命なら呼び捨てを避け敬称を付ける**（例: 「長生淳さん」。クラシック方面に寄せるなら「氏」も可）。故人（バルトーク等の歴史上の人物）は呼び捨てで可。

ただし **作品末尾のクレジット表記**（例: 「長生淳『翠風の光』（「四季連禱」より）」）は敬称略の慣習に従い呼び捨てのまま — ここを区別する。

**Why**: 存命の作曲者への敬意。本人や関係者の目に触れうる外部発信では特に配慮したい。

## 6. ドキュメント設計の流儀

### 6.1 確立理論の語彙で裏打ちする

構成・執筆支援ドキュメントや汎用フレームワークを設計するときは、思いつきの作法集ではなく **確立した理論体系（物語論・修辞学・PREP 等）の語彙を土台** にし、必ず実務への転用例とセットで提示する。学術用語の羅列で終わらせない。

実例: [.claude/storytelling/](../storytelling/)（物語論）、[.claude/coherence/](../coherence/)（Halliday & Hasan + RST）。プロジェクトの開発原則（[15-principles.md](./15-principles.md) の体系志向）とも一致。

**出典**: storytelling フレームワーク設計時の計画レビューで「物語論の用語・手法・不変条件を加味してほしい」と明示指示。

## 7. 機械チェックとの対応

`just check-content` が検査するのは次の規約のみ（それ以外は人間 + エージェントのレビューで守る）:

| 規約 | 検査対象 | ルール ID |
| :--- | :--- | :--- |
| §1 ベタ詰め | `src/content/cfp/*/index.md`, `src/content/blog/*.md` | `betsume` |
| §2.1 Markdown 装飾なし | `src/content/cfp/*/index.md` | `no-decoration` |
| §2.2 所要時間なし | `src/content/cfp/*/index.md` | `no-duration` |
| §3 見出しの作業日付 | `src/content/cfp/*/{index,drafts}.md`, `src/content/blog/*.md` | `no-edit-date` |

誤検知（引用文中の固有タイトル等）は、該当行に `<!-- check-content: ignore -->` を付けて免除できる。恒久的な免除（提出済みアーカイブ等）はスクリプト内の免除リストに追加する。
